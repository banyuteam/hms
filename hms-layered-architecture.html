HMS layered architecture

How hms_workspace, hms_services and hms_database fit together today, from the screen down to the data. Layers talk only to the layer below them through a versioned contract. The legacy Khanza database sits outside every layer and is only ever read.

Three paths through the layers

Path A · in use today

Read a visit timeline

The main path for every EMR window.

  1. WebEMR window calls GET /api/v1/encounters/{no}/timeline with the session cookie
  2. nginxproxies to hms-services
  3. IAMsession valid, encounter.clinical.read at the session facility
  4. clinical/runs the fixed timeline statements through legacyhms against Khanza
  5. auditevent written in PostgreSQL; on failure the answer is 503 with no data
  6. Webmaps clinical-timeline-v1 into the EMR windows
Path B · built, no screen yet

Register a patient natively

Allowed only once the patient domain is cut over.

  1. ClientPOST /api/v1/patient-records with a client-made id (safe retries)
  2. IAMpatient.register
  3. native/patientapplies registration rules
  4. recordtxsets organization, user actor and request id for the transaction
  5. Databaseguard checks authority is native; otherwise HM001, returned as 409 domain_not_native
  6. Databasewrites version 1, history row and audit event in one commit
Path C · built, opt-in worker

Bridge a Khanza patient

Fills the canonical record while Khanza still owns the domain.

  1. Bridgetakes the lease and reads its checkpoint
  2. legacyhmsPatientScan: bounded primary-key range on pasien
  3. Mappingpasien/1, row hash; unchanged rows are skipped
  4. canonical/patientwrite as service legacy-bridge
  5. Databaseguard checks authority is legacy; crosswalk and issues recorded
  6. Bridgeadvances the checkpoint only while it still holds the lease
Domain authority, per organization and domain: legacy→cutover→native (abort: cutover → legacy; native is final)

Deployment topology (deployment/compose.yaml)

  • One-shot steps in order: postgres → db-bootstrap → db-migrate → org-setup
  • Long-running: hms-services, hms-web, clamav; legacy-bridge behind a profile
  • Networks hms-private and hms-scan; volumes for PostgreSQL, files and virus signatures
  • Passwords and keys as mounted secret files, never environment values
  • Separate compose.production.yaml and a monitoring stack (Prometheus, Grafana, Loki, Alertmanager)
